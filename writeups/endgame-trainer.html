CASE-02 Resolved Web Exploitation / Client-Side Bypass

Endgame Trainer: Client-Side Checkmate Bypass

Room TryHackMe — Endgame Trainer
JavaScript API Abuse Web Exploitation

Objective

A web-based "chess endgame trainer" presents a mate-in-one puzzle, but blocks the winning move client-side with a fake threatening popup. Bypass the client-side restriction and retrieve the flag from the server.

The Setup

The app is a chess trainer starting from the position:

6k1/5ppp/8/8/8/8/5PPP/R5K1 w - - 0 1

White to move, with an obvious mate-in-one: Ra8# (rook from a1 to a8 — back-rank mate, since Black's king is boxed in by its own f7/g7/h7 pawns).

Attempting to play this move in the UI triggered a fake Windows-style error dialog:

"I'll shut down your PC if you play that."

This is purely a scare tactic rendered in HTML/CSS/JS — it has no actual capability to affect the user's system.

Source Review

Reviewing js/app.js revealed the actual mechanism behind the block, in a function called before any move is sent to the server:

function preMoveCheck(from, to, promotion) {
  const probe = new Chess(game.fen());
  let result;
  try {
    result = probe.move({ from, to, promotion: promotion || undefined });
  } catch (e) {
    result = null;
  }
  if (result && probe.isCheckmate()) {
    showSystemNotice("I'll shut down your PC if you play that.");
    return false;
  }
  return true;
}

Key takeaway: the app simulates every candidate move locally, on a throwaway copy of the board (probe), before sending anything to the server. If the simulated move results in checkmate, it shows the fake warning and returns false, which stops doMove() from ever calling sendMove(). In other words:

The checkmate-blocking logic exists entirely in client-side JavaScript that the user fully controls.

The move validation and flag-issuing logic, by contrast, live server-side behind /api/move — a call the client makes with fetch() once preMoveCheck approves it.

Exploitation

Since the restriction never reaches the server, it can be bypassed by calling the API directly from the browser's DevTools console, skipping the UI (and preMoveCheck) entirely:

fetch('/api/move', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ from: 'a1', to: 'a8' })
}).then(r => r.json()).then(console.log)

Note: if the server-side game state has drifted from the intended starting position (e.g., from earlier testing), reset first:

fetch('/api/reset', { method: 'POST' }).then(r => r.json()).then(console.log)

Then resend the mating move. The server validated the checkmate and returned the flag in the JSON response.

Result

Flag:

THM{cl13nt_s1d3_ch3ckm4t3}

Takeaway

This challenge is a clean illustration of a fundamental web security principle: never trust client-side validation for anything security- or logic-critical. The client is fully under the user's control — any check, restriction, or "gate" implemented only in JavaScript running in the browser can be inspected, understood, and bypassed by simply calling the underlying API directly. Legitimate authorization and game-state logic must be enforced server-side, which — fittingly — is exactly where this app's actual checkmate detection and flag issuance lived.
